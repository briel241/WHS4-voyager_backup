# 시나리오 작성 템플릿

> 모든 시나리오 문서는 아래 9개 절을 이 순서로 갖는다.
> 새 시나리오를 쓸 때 이 파일을 복사해 채운다.

작성 원칙 세 가지.

1. **행위로 쓴다.** "A가 B를 한다" 형태로 서술해야 읽히고, 행위자 구현이 바로 도출된다.
2. **재현 가능하게 쓴다.** 같은 설정값으로 같은 결과가 나와야 한다.
3. **위험을 먼저 쓴다.** 이 프로젝트의 목적은 기능 확인이 아니라 **영향 실증**이다.
   §6이 비어 있으면 그 시나리오는 왜 하는지 설명하지 못한다.

---

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 시나리오 ID | `SC-VDE-000` |
| 목적 | 한 문장 |
| 분류 | 트래픽 유형 (소용량·주기적 / 대용량·일방적 / 양방향 등) |
| `data_type` | API 계약의 분류. 없으면 "미배정"이라고 쓰고 §9에 남긴다 |
| 위험 등급 | 최상 / 상 / 중 (§6의 결론) |
| 상태 | 구현됨 / 링크 계층 대기 / 결정 대기 |

---

## 2. 참여자별 행위

**"A가 B를 한다" 형태로 쓴다.** 각 참여자가 무엇을 하는지가 곧 행위자 구현 명세다.

| 참여자 | 식별자 | 하는 일 |
| --- | --- | --- |
| ROC | | |
| MASS | | |
| (공격자) | | 공격 시나리오에서만 |

시간 순 서술이 필요하면 문장으로 덧붙인다.

- ROC가 …한다.
- MASS가 …하면 …한다.

---

## 3. 통신 설정값

같은 조건을 재현하기 위한 값이다. 빠진 값이 있으면 결과가 재현되지 않는다.

| 항목 | 값 |
| --- | --- |
| 물리 채널 | 100 kHz 등 |
| Link ID | |
| TBB 동기화 | 필요 / 불필요 |
| 시간 동기화 | 필요 / 불필요 |
| 채널 조건 | 동축 루프백 / 손실률 등 |
| 사전 조건 | 신뢰 앵커 탑재 여부 등 |

---

## 4. 송수신 데이터

| 항목 | 내용 |
| --- | --- |
| 형식 | |
| 크기 | 최대·평균 |
| 내용 | 주요 필드 |
| 표준 근거 | 있으면 조항, 없으면 "프로젝트 정의"로 표시 |

**표준에 없는 필드는 반드시 표시한다.** 나중에 근거를 물었을 때 답할 수 있어야 한다.

---

## 5. 메시지 흐름

전송 경로(Message Type)와 순서를 적는다. 크기가 경로를 좌우하므로 계산을 함께 남긴다.

```text
ROC                          MASS
 │──[1] Type ... ──────────▶ │
 │◀─[2] Type ... ─────────── │
```

용량 계산이 필요하면 여기에 둔다.

```text
Link ID 17 packet     234 byte
  − CRC-32              4
  − 헤더                ...
  = 가용               ... byte
```

---

## 6. 위험 (Risk) ★

**이 절이 시나리오 선정의 근거다.** 구상도의 공격 분류를 축으로 쓴다.

| 공격 | 방법 | MASS에 미치는 영향 | 등급 |
| --- | --- | --- | :-: |
| 데이터 위조 | | | |
| 신분 사칭 | | | |
| 재전송 | | | |
| 차단 (DoS) | | | |
| 탈취 | | | |

**영향은 "배에 무슨 일이 나는가"로 쓴다.** "무결성이 깨진다" 같은 서술은 영향이 아니다.

- **직접 위험**: 조작하면 배가 즉시 다르게 움직인다
- **간접 위험**: 조작하면 다른 공격이 가능해진다

둘 중 어느 쪽인지 명시한다. 실증 방법이 달라진다.

---

## 7. 예상 결과

정상 동작에서 무엇이 관측되어야 하는가. **관찰 도구로 확인 가능한 형태**로 쓴다.
