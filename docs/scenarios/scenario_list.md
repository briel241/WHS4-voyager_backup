# 개발 대상 시나리오 목록

> MASS/ROC가 VDE-TER로 주고받는 데이터를 시나리오 단위로 정리한다.
> 작성 형식은 [`TEMPLATE.md`](TEMPLATE.md)를 따른다.

프로젝트 제목 **"보안성 검토 및 암호통신 기술 개발"** 의 두 목적이 두 축이 된다.

| 축                   | 답하는 질문                            | 정렬 기준        |
| ------------------- | --------------------------------- | ------------ |
| **보안성 검토** (영향 실증)  | 데이터가 조작·차단되면 **배에 무슨 일이 나는가**     | **위험(Risk)** |
| **암호통신 개발** (방어 설계) | 그 조작을 **어떤 암호로 막고, 우리가 무엇을 만드는가** | **암호 메커니즘**  |

## 0. 개발 대상 시나리오 선정 현황

개발 대상은 **3개 시나리오**다 — 하나는 확정, 둘은 선정 예정.

| 슬롯      | 시나리오                          | 데이터                     | 상태           |
| ------- | ----------------------------- | ----------------------- | ------------ |
| **확정**  | **공개 키 인증서 송수신** (SC-VDE-001) | X.509 인증서·CRL           | ✅ **확정**     |
| 선정 예정 ① | 서비스별 고안 → 우선순위 평가로 선별         | **S-421 Route Plan 유력** | 후보 평가 중      |
| 선정 예정 ② | 위 둘 중 하나는 **MASS 조작 데이터** 포함  | 미정                      | **멘토 자문 요청** |

**선정 방법**: IALA G1117이 제시하는 VDES 활용 시나리오에서 서비스를 서비스별로
고안(§1) → **규격 완성도·침해 파급력·use case 정리도** 기준으로 우선순위 평가 → 2개 선별.

**예상 산출물**: 개발 대상 시나리오 정의 + **시나리오 구현 코드**.

> **MASS 조작 데이터**(MASS가 내보내는 데이터를 위조·조작하는 공격 시나리오)는 구현
> 방법에 대해 멘토 자문을 요청한 상태다. §6-2 참조.

### 0.1 두 축은 유지된다 — 선정과 별개의 분석 틀

위 선정은 "어떤 **데이터/서비스**를 쓸까"의 문제다. 그 데이터를 **어떻게 지킬까**는 별도
분석 축으로 남는다(§2 암호 메커니즘). 확정된 인증서 송수신(SC-VDE-001)이 바로 그 방어의
기반(PKI 키 분배)이라, 데이터 축과 암호 축이 SC-VDE-001에서 만난다.

**실증 원칙 — 풀스택으로 보인다.** 공격 실증은 비트 주입이 아니라 **실물 링크·RF를
통과**해야 성립한다 — 동형 체계(항공 CPDLC) 공격 연구(Ziazi et al., USENIX Sec 2026)가
"응용 계층만으론 부족하다"를 확인했다. 링크 계층 팀원과의 협업 지점이다.

> 근거: IALA G1117(VDES 활용 시나리오) · IALA *Use Cases on VTS Digital Communications* ·
> ITU-R M.2092-2 · `docs/vde_service_api(prototype).md` · 구상도 ·
> TESLA 논문(Lee & Lee, IEEE Access 2025) · CPDLC 공격 논문(Ziazi et al., USENIX Sec 2026)

## 1. 서비스별 데이터 인벤토리 (선정의 1차 근거)

IALA G1117의 VDES 활용 시나리오에서 서비스를 뽑아, 각 서비스가 쓰는 데이터·규격·침해
파급력을 정리한다. **이 표가 시나리오 선정의 1차 근거다** — 규격이 잘 정의됐고 파급력이
높은 데이터일수록 우선순위가 높다.

| 서비스              | 규격            | 규격 완성도         | 기밀성 파급 | 무결성 파급 | 대응 시나리오              |
| ---------------- | ------------- | -------------- |:------:|:------:| -------------------- |
| 노선 계획 교환         | **S-421**     | Ed.1 발행 완료     | **상**  | **상**  | SC-VDE-005 (유력·구현됨)  |
| 선박통항관제(VTS)      | S-212         | 0.7.3 개발 중     | 중      | 상      | SC-VDE-011 (잠정)      |
| 물류·항만 서비스        | S-211         | Draft (1.0.0)  | **상**  | 중-상    | SC-VDE-012 (항행안전 밖)  |
| 항행 경보            | S-124         | Ed.2.0.0 발행 완료 | 하      | 상      | **SC-VDE-009 (구현됨)** |
| 실시간 기상·조석        | S-104/411/412 | 일부만 운용판        | 하      | 상      | **SC-VDE-010 (메시지)** |
| 선박 기상관측 보고       | BUFR          | 상용 중           | 중      | 중      | **SC-VDE-013 (메시지)** |
| **공개 키 인증서 송수신** | X.509         | —              | —      | **최상** | **SC-VDE-001 ✅확정**   |

### 1.1 두 가지 발견

**① 무결성은 데이터 종류와 무관하게 높다.** 선박 한 척의 가치가 억 단위이고, 그 배가
주고받는 데이터가 변조되면 파급력이 작을 수 없다. → **무결성(인증)이 프로젝트의 1차
관심사**인 근거. 확정 시나리오가 인증서 송수신인 것과 맞물린다.

**② 기밀성은 데이터에 따라 갈린다 — 이전 판단을 정밀화한다.**

- **방송 안전정보**(경보 S-124, 기상 S-104)는 기밀성 **하** — 원래 공개돼야 하는 정보.
- **개별 선박 정보**(노선 S-421, 화물 S-211)는 기밀성 **상** — 노출되면 **표적화**된다.

노선·기항 정보 노출이 선박 공격으로 이어지는 관계는 실제 사례로 뒷받침된다(2024~2026
후티의 선박 공격에서 기항 이력·운항 방향이 표적 선정에 활용된 정황, 특히 공격 회피를
위해 선박들이 AIS를 끄기 시작한 정황). 즉 **Route Plan에는 무결성뿐 아니라 기밀성도
요구된다** — 인증만으론 부족하고 **암호화가 필요할 수 있다**(§6-3 범위 결정).

### 1.2 왜 S-421 Route Plan이 유력한가

| 근거               | 내용                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------- |
| **use case 정리도** | IALA *VTS Digital Communications* Use Cases에서 **Route Function이 가장 잘 정리**됨(다른 기능은 미정리) |
| **규격 완성도**       | S-421 Ed.1 발행 완료 → 데이터 교환의 프로토콜 문제를 파악하기 좋음                                            |
| **기밀성 근거**       | 노선 노출 → 표적화 관계가 성립 → 기밀성 보장의 필요가 실증됨                                                   |

우리 SC-VDE-005(항로 지시·추종)가 이미 이 데이터를 다룬다 — 단, legacy IFM(FI=28)을
차용했고 S-421이 그 현대적 판본이다. 선정 시 **S-421 정합**을 SC-VDE-005에 반영한다.

### 1.3 직접 위험과 간접 위험 (실증 방법의 구분)

- **직접 위험** — 조작하면 배가 즉시 다르게 움직인다. 관찰 도구 **항적 한 장**으로 끝난다.
  (항로 지시·제어권 전환·비상 개입·전자해도)

- **간접 위험** — 조작하면 **다른 공격이 가능**해진다. 직접 시나리오를 무대로 빌리는
  **2단 실증**이 필요하다. (인증서·TBB·AIS 인증값)
  
  > 인증서가 오염되면 → 위조 명령이 통과하고 → **배가 항로를 벗어난다.**

## 2. 암호 메커니즘 인벤토리 (두 번째 축)

표준에서 뽑은 암호 지점과, 각 지점에서 **공격할 것 / 개발할 것**을 정리한다.

| 암호 메커니즘             | 표준 상태 (M.2092-2)                           | 여기서 하는 일                 | 성격     |
| ------------------- | ------------------------------------------ | ------------------------ |:------:|
| **인증 부재 (CIV)**     | Type 4/90/13/92/93 서명 필드 **0개**            | ★ 위조·사칭 실증 (택함)          | 공격     |
| **제약 채널 브로드캐스트 인증** | 불리틴 6+64 B ECDSA, Link ID 11 강제 → fragment | ★ ECDSA vs TESLA 비교 (택함) | **개발** |
| 서명 검증 우회            | ECDSA 있으나 valid-until 창 존재                 | 유효기간 내 재전송, 48비트 지문      | 공격     |
| 다운그레이드              | signed/unsigned segment 공존                 | signed 지점에 unsigned 강제   | 공격     |
| CRL 오프라인 창          | "CA 불가 시 CRL 저장" 요구                        | 폐기 키 계속 신뢰 구간            | 공격     |
| 키·신뢰 부트스트랩          | CA·키 배포·앵커 주입 **공란**                       | 프로토콜 제안                  | 개발     |
| 물리·행위 기반 탐지         | 표준에 없음                                     | 송신원 정합성·이상 탐지 (관찰 도구 확장) | 방어     |

> ★ 표시가 이번 판에서 **택한 공격 표적과 개발 초점**이다. 나머지는 후속 확장 대상.
> 맨 끝 행은 CPDLC 연구의 시사점 — 표준 암호 배포가 "10년 뒤"라, 그 공백을 메울 중간
> 방어로 RF 지문·위치 정합성 검사가 제시된다. 우리 관찰 도구가 그 초기 형태다.

### 2.1 확정된 암호 사실 (표준 원문 확인)

- **M.2092-2는 ECDSA 일변도** — TESLA·지연 키·대칭 MAC 언급 **전무**.
- **BBSC는 Link ID 11 강제** (§A4-4.8.1, *"All transactions in the BBSC shall use Link ID 11"*).
- 불리틴 인증 = 지문 6 B + ECDSA 서명 64 B = **70 B > packet 54 B** → 연속 fragment로 분할.
- 따라서 "ECDSA가 안 들어간다"가 아니라 **"들어가되 비싸다"** 가 정확한 문제 정의.

## 4. 시나리오 요약

### SC-VDE-005 · 항로 지시와 추종 · 유력 후보 (S-421)

상세: [`SC-VDE-005-route-guidance.md`](SC-VDE-005-route-guidance.md)

- **선정**: 나머지 2개 슬롯의 **유력 후보** — 데이터가 **S-421 Route Plan**과 정합하고
  (§1.2), 노선 노출→표적화로 기밀성 근거까지 성립. MASS 조작 데이터(공격군)의 무대이기도.
- **행위**: ROC가 항로를 지시한다 → MASS가 검증하고 수락한다 → MASS가 항로를 따라간다
- **암호 지점**: **인증 부재**. Type 92는 segment 계층 밖이라 서명이 없다.
- **공격(MASS 조작 데이터)**: ROC MMSI를 **사칭**해 위조 항로 주입 → 항적 이탈
- **상태**: 정상 동작 구현·문서 완료. 선정 시 **S-421 정합 + 공격군 구현**이 다음 단계

### SC-VDE-008 · 제약 채널 브로드캐스트 인증 ★ 개발 초점

상세: [`SC-VDE-008-broadcast-authentication.md`](SC-VDE-008-broadcast-authentication.md)

- **개발 대상**: 불리틴 보드 인증을 ECDSA(표준) vs TESLA(대안)로 비교·평가
- **문제**: BBSC=Link ID 11 강제 + 인증 70 B > packet 54 B → ECDSA는 fragment로 비싸다
- **대안**: TESLA 80비트 MAC(10 B) + 지연 키 공개. 리포 논문의 권장값·방법론 활용
- **산출**: 오버헤드·성공률·지연·위조저항 정량 비교. "어떤 조건에서 어느 방식이 유리한가"

### SC-VDE-006 · 제어권 전환

- **행위**: MASS 자율 항행 중 → ROC가 이양 요청 → MASS 승인, RC로 전환
- **데이터**: 이양 요청/승인/거부/반환. **표준 메시지 없음 — 프로젝트 정의 필요**
- **위험**: 이양 위조 → 제어권 탈취. 반환 위조 → 조타 주체 상실. 응답 차단 → 상태 불일치
- **암호 지점**: 인증 부재 (SC-VDE-005와 동일 표적). 상태 모델은 `mass_roc_background.md` §2.5~2.6

### SC-VDE-007 · 비상 원격 개입

- **행위**: MASS 이상 감지 → ROC가 비상 정지·회피 지시 → MASS 즉시 실행
- **데이터**: 비상 명령(최우선). **표준 메시지 없음**
- **위험**: **차단이 가장 위험**. 위조보다 "비상 명령 미도달"이 치명적. 우선순위 §A1-2.6

### SC-VDE-001 · 인증서·CRL 전송 ✅ 확정

상세: [`SC-VDE-001-x509-certificate.md`](SC-VDE-001-x509-certificate.md)

- **선정**: **개발 대상 확정 시나리오** (§0). 3개 슬롯 중 첫 번째.
- **행위**: ROC가 인증서 전송 → MASS가 재조립·검증 후 신뢰 저장소 반영
- **데이터**: X.509 DER 최대 1,024 B → Link ID 17에서 **6 fragment**
- **암호 지점**: **CRL 오프라인 창**. 서명 안 깨고 갱신만 막으면 폐기 키 계속 신뢰
- **간접**: 영향은 SC-VDE-005를 무대로 (오염 인증서 → 위조 항로 통과)
- **암호 축 연결**: 여기서 나눠준 공개키로 방송을 검증하는 게 SC-VDE-008

### SC-VDE-004 · 전자해도 전송

- **행위**: ROC가 갱신 해도 전송 → MASS가 검증 후 반영
- **데이터**: S-101 등. 대용량 → data session
- **위험**: 위조 수심·장애물 → **좌초**. SC-VDE-001과 링크 기능 동일, 위험이 달라 별개

### SC-VDE-002 · TBB 브로드캐스트

- **행위**: 제어국이 서비스영역·슬롯맵 브로드캐스트 → MASS가 서명 검증 후 반영
- **암호 지점**: **표준에서 서명이 붙는 유일한 브로드캐스트 지점** (지문 6 B + ECDSA 64 B)
- **제약**: BBSC는 Link ID 11 강제 → 11과 17 병행 필요
- **위험**: 서명이 있어 위조는 어렵다. **차단이 실효 공격** — 슬롯맵 못 받으면 통신 마비
- **연결**: **SC-VDE-008의 무대.** "인증 있음 vs 없음" 대조군이자, 그 인증을 어떻게
  더 싸게 만들지(TESLA)의 대상

### SC-VDE-003 · AIS 인증·무결성 값 ★ 구현됨

- **행위**: ROC가 AIS 인증값 브로드캐스트 → MASS가 자신이 들은 AIS 원본과 대조 검증
- **데이터**: 지문 48 + MMSI 30 + 타입 6 + 유효기간 32 + 서명 512 bit = **82 B**
- **암호 지점**: 서명 검증. 공격 5종(위조·원본위조·미신뢰인증서·원본부재·유효기간) 검증됨

### SC-VDE-009/010/013 · 서비스 카탈로그 (압축 스키마 구현됨)

상세: [`../compact_message_schemas.md`](../compact_message_schemas.md)

- **009 항행 경보 (S-124)**: **육상국이 경보 방송 → MASS 반영**까지 구현. 압축 스키마
  (Message ID 5) + 행위자 연결(`issue_warning`/수신·저장·유효기간 만료·위험구역 인식) +
  데모 `apps/warning_broadcast.py` + 시험. **지금 실물 링크(Type 93)를 통과해 동작한다.**
- **010 환경 정보 (S-104/411/412)**: 압축 스키마(Message ID 6) 구현. 방송용 보완 경로이며
  전체 격자(HDF5)는 data session 유지. 행위자 연결은 미착수.
- **013 기상관측 보고 (BUFR)**: 압축 스키마(Message ID 7) 구현. ship→shore. 행위자 미연결.

> 이 셋은 서비스 카탈로그의 데이터 시나리오다. **메시지 계층은 만들어졌으나**, 선정될
> 2개 슬롯에 드는지는 §1 기준 평가로 정한다(구현됐다고 자동 선정되는 것은 아니다).

## 5. 진행 순서

확정 시나리오 착수 + 나머지 2개 선정을 병행한다.

```text
[확정 — 착수 준비]
  SC-VDE-001  인증서·CRL 송수신    ← 링크 data session 대기. 그 전 B2~B4(DER·저장소) 선행 가능
  SC-VDE-008  ECDSA vs TESLA      ← 001의 짝(방송 인증). 링크 RF와 독립적으로 시뮬 평가 가능

[선정 — 나머지 2개 확정하는 절차]
  1) IALA G1117 서비스별 시나리오 고안        (§1 인벤토리)
  2) 규격 완성도·침해 파급력·use case 정리도로 우선순위 평가
  3) 2개 선별 (하나는 MASS 조작 데이터 → 멘토 자문)
     · 유력: SC-VDE-005 항로(S-421) — use case·규격·기밀성 근거 모두 성립
     · MASS 조작 데이터 후보: 005 공격군 / 006 / 007

[완료 — 서비스 카탈로그 메시지 계층]
  SC-VDE-009 항행 경보   압축 스키마(ID 5) + 행위자 연결 + 실물 링크 통과 데모 ✓
  SC-VDE-010/013        압축 스키마(ID 6/7) 구현 ✓ (행위자 연결은 미착수)

[지금 가능한 구현]
  SC-VDE-005 공격군   ROC 사칭 위조 항로 주입 → 항적 이탈   ← 정상군 완료, 공격군만
  SC-VDE-008 시뮬     C2 TESLA 키체인 → C3 지연공개 → C4 성공률
  SC-VDE-010/013 연결 육상국 환경 방송 / MASS 기상 보고 (009 패턴 재사용)
```

### 5.1 실증 짝짓기

간접 위험 시나리오는 직접 시나리오를 무대로 빌린다.

| 간접                   | 무대             | 보여줄 것                                  |
| -------------------- | -------------- | -------------------------------------- |
| SC-VDE-001 인증서       | SC-VDE-005 항로  | 인증서 오염 → 위조 항로 통과 → **항적 이탈**          |
| SC-VDE-003 AIS 인증값   | SC-VDE-005 항로  | 위조 AIS → 회피 오판                         |
| SC-VDE-002 TBB       | 전체             | 슬롯맵 차단 → 통신 마비                         |
| **SC-VDE-008 인증 개발** | SC-VDE-002 TBB | ECDSA vs TESLA로 그 브로드캐스트를 **어떻게 지키는가** |

## 6. 결정이 필요한 사항

| #   | 항목                          | 영향                                          | 결정 주체        |
|:---:| --------------------------- | ------------------------------------------- | ------------ |
| 1   | **나머지 2개 시나리오 선별**          | §1 기준으로 우선순위 평가 → 개발 대상 확정                  | 프로젝트         |
| 2   | **MASS 조작 데이터 구현 방법**       | 선정될 공격 시나리오의 실증 방식 — **멘토 자문 요청 중**         | 멘토 · 프로젝트    |
| 3   | **Route Plan 기밀성 → 암호화 범위** | S-421 기밀성이 상(표적화). 인증만으론 부족 → **암호화 포함 여부** | 프로젝트         |
| 4   | 운항 메시지용 `data_type`         | 위험 최상 005/006/007이 API 분류 부재로 막힘            | API 소유자      |
| 5   | TESLA 링크계층 구현 담당            | SC-VDE-008 — 시뮬 평가는 본 과제, RF 구현은 미정         | 프로젝트 · 링크 계층 |
| 6   | 제어권 전환·비상 명령 메시지 정의         | SC-VDE-006/007 (표준 없음)                      | 프로젝트         |
| 7   | data session·Link ID 11     | SC-VDE-001/002/004                          | 링크 계층        |

**1·2번이 지금 급하다** — 개발 대상 3개 중 확정은 인증서 송수신뿐이고, 나머지 2개(특히
MASS 조작 데이터)는 선별과 멘토 자문을 거쳐야 확정된다.

**3번은 방향을 가르는 결정이다.** 지금까지 프로젝트는 **무결성(인증)** 에 집중했다 —
대부분 데이터가 "숨길 필요는 없지만 위조되면 안 되는" 방송 정보였기 때문이다. 그러나
**Route Plan(S-421)은 기밀성도 상**이다(노선 노출 → 표적화, §1.1). 이 데이터를 쓰면
**서명(무결성)만으로는 부족하고 암호화(기밀성)가 필요**해진다. SECOM(IEC 63173-2)이
응용 계층 종단 암호화를 제공하므로, "TESLA(링크 인증) + SECOM(응용 암호화)" 조합이
후보다. 암호화를 범위에 넣을지 결정해야 한다.
