# MASS/ROC 시나리오 — 동작 원리와 사용법

이 문서는 **무엇이 어떻게 동작하는지**와 **상황별로 어떤 명령을 순서대로 치면 되는지**를
정리한다. 터미널만 있으면 따라 할 수 있게 썼다.

---

## 1. 큰 그림 (먼저 이것만)

```
ROC(육상 관제)                                            MASS(선박)
  RocAgent                                                 MassAgent
    │ ① 보낼 데이터를 만든다                                  ↑ ④ 받아서 검증·반영하고
    │   (인증서 / 노선 / 조종 명령)                            │    ACK를 돌려준다
    ▼ ② payload(바이트)로 바꾼다 (PI: codec / bridge)         │
    └────── ③ VDETER 링크가 전파로 나른다 (팀원 담당) ─────────┘
```

- **ROC/MASS(우리 코드)** — 무슨 데이터를 주고받을지 만들고 검증한다. 전파가 어떻게
  나가는지는 모른다.
- **VDETER(팀원 코드)** — 그 바이트를 실제로 실어 나른다.
- **시나리오 3개** — ① X.509 인증서 송수신 ② S-421 노선 계획 교환 ③ MASS-ROC 원격 조종.
- **로그·분석** — 시나리오를 돌릴 때마다 무슨 일이 있었는지 시간순으로 기록하고,
  규격대로 됐는지 **합격/불합격**을 판정해 `results/`에 저장한다.

**핵심**: 장비(USRP B210)가 없어도 소프트웨어만으로 시나리오 전체를 돌리고, VDETER
전송까지 시뮬레이션할 수 있다. 장비는 맨 마지막 실 RF 검증에만 필요하다.

### 2-0. GitHub에서 무엇을 받나

```bash
git clone <저장소 URL>
```

```bash

```

```bash
git switch integration/mass-roc-stage7
```

`git clone`으로 **저장소에 있는 것은 전부** 받아진다. 무엇이 들어있는지:

| 폴더                       | 내용                              | 필요 상황        |
| ------------------------ | ------------------------------- | ------------ |
| `common/` `MASS/` `ROC/` | 응용 계층 코드 (핵심)                   | 전부           |
| `apps/` `tests/`         | 실행·시연·시험                        | 전부           |
| `docs/`                  | 문서(이 파일 포함)                     | 전부           |
| **`VDETER/`**            | **실 VDE-TER 링크 패키지** (저장소에 포함됨) | 상황 C, 상황 D-② |

**저장소에 없는 것(gitignore) — 따로 받아야 하는 것:**

| 항목                | 무엇                         | 언제 필요             | 어떻게           |
| ----------------- | -------------------------- | ----------------- | ------------- |
| `VDETER_Link/`    | 구 단방향 링크 플로우그래프(stage-1)   | **불필요(LEGACY)** — 구식 D-① 벤치 전용이었음 | (더 이상 쓰지 않음) |
| `references/`     | 배경 논문 PDF·Faraday Cage 계획서 | 참고용(선택)           | 팀 공유 폴더       |
| `results/` `grc/` | 실행 산출물·GNU Radio 빌드물       | 불필요(자동 생성)        | —             |

**상황별로 무엇까지 있어야 하나:**

- **상황 A·B** (시나리오 재현·시험): `git clone`만. 추가 설치·파일 없음.
- **상황 C** (무선 시뮬레이션): `git clone` + `cryptography`(2-2). **`VDETER/`는 이미 저장소에 있다.**
- **상황 D** (Stage 7 실물 RF): `git clone` + `cryptography` + 3노드 장비(Pi 5 + B210 3대).
  저장소의 `VDETER/` Stage 7 launcher·B210 백엔드 사용. 구식 ①(간이 벤치)만 별도
  `VDETER_Link/` 사본이 필요했으나 현재는 쓰지 않는다.

### 2-1. 파이썬 준비

터미널을 열고 프로젝트 폴더(`voyager_3` 저장소 루트)로 이동한다. 아래 명령의
`python`은 각자의 인터프리터다 — Linux/macOS는 `python3`, Windows는 `python`
(또는 crypto가 이미 설치된 `VDETER\.venv\Scripts\python.exe`). 직접 실행
스크립트는 UTF-8 출력을 스스로 정착시키므로(`common/textout.py`) Windows CP949
콘솔에서도 `-X utf8` 없이 그대로 돈다.

파이썬은 용도에 따라 두 갈래다. 이걸 알면 나머지가 쉽다.

| 용도                 | 필요한 것                  | 어디서    |
| ------------------ | ---------------------- | ------ |
| 시나리오 재현 · 단위테스트    | 기본 파이썬 (설치 불필요)        | 상황 A·B |
| VDETER 무선 종단 시뮬레이션 | `cryptography` 설치된 파이썬 | 상황 C   |

### 2-2. (상황 C를 할 사람만) 전용 가상환경 1회 준비

> ⚠️ GNU Radio가 쓰는 시스템 파이썬에 직접 설치하지 말 것. 전용 venv를 따로 둔다.
> Windows에서 `VDETER\.venv`(uv 관리, cryptography 포함)가 이미 있으면 그것을
> 그대로 쓰면 되고, 아래 venv를 새로 만들 필요가 없다.

```bash
# Linux/macOS
python3 -m venv .venv-crypto
.venv-crypto/bin/pip install cryptography

# Windows (PowerShell)
python -m venv .venv-crypto
.venv-crypto\Scripts\pip install cryptography
```

**중요**: 설치는 venv에 했으므로, 실행도 반드시 그 venv의 파이썬
(`.venv-crypto/bin/python` 또는 `.venv-crypto\Scripts\python`)으로 한다.
시스템 파이썬으로 돌리면 cryptography가 없다고 나온다. (venv를 activate하면
그 터미널에서는 `python`이 venv를 가리킨다.)

## 상황 A — 시나리오를 골라 돌려본다 (장비·설치 불필요) ⭐

가장 자주 쓰는 방법. **대화형 메뉴**로 고르면 바로 실행된다.

```bash
python3 apps/scenario_runner.py
```

그러면 이런 메뉴가 뜬다:

```
=== MASS/ROC 시나리오 재현 (대화형) ===
  1) SC-VDE-005  S-421 노선 계획 교환
  2) SC-VDE-006  MASS-ROC 원격 조종
  3) SC-VDE-001  X.509 인증서 송수신  [현재 미지원 — Data Session 미완성]
  a) 전체 실행 (미지원 시나리오는 미지원 결과만 출력)
  q) 종료

선택 >
```

- **번호(1·2·3)** 또는 **시나리오 ID**를 입력하면 즉시 실행하고, 시간순 타임라인 +
  합격/불합격 판정을 보여준 뒤 **다시 메뉴로 돌아온다.** SC-VDE-001을 고르면
  실행 대신 **구조화된 미지원 안내**(사유 포함)가 나온다.
- **`a`** = 전체 실행, **`q`** = 종료.
- 실행할 때마다 로그가 `results/`에 저장된다.

### 명령을 직접 치고 싶으면 (스크립트·자동화용)

```bash
python3 apps/scenario_runner.py list
```

```bash
python3 apps/scenario_runner.py run SC-VDE-005
```

옵션: `--json`(기계용 JSON 출력) · `--no-save`(로그 파일 안 남김) · `--now <숫자>`(기준 시각 고정, 재현용).

### 결과 읽는 법

- **타임라인**: `+0.30s  ROC->MASS  send  조종 데이터 …` 처럼 누가 언제 무엇을 했는지.
- **판정**: `[PASS] ack-status …`, 맨 위에 `— 합격 / 불합격`.
- **파일**: `results/SC-VDE-00X_<시각>.json` 에 전체 로그가 저장된다.

```bash
ls results
```

## 상황 A-2 — 화면으로 보면서 조종한다 (콘솔 GUI, 설치 불필요) ⭐

시나리오를 "돌려보는" 것이 상황 A라면, 이건 **배가 움직이는 것을 보면서 직접
명령을 내리는** 것이다. 브라우저 두 창을 나란히 놓고 쓴다.

```bash
python3 apps/console_server.py
```

주소가 출력된다. **터미널은 켜둔 채로** 브라우저에서 두 개를 연다.

```text
http://localhost:8420/roc     육상 관제 — 해도를 클릭해 항로·조종을 발행한다
http://localhost:8420/mass    본선 — 위치·침로·제어권·수신 로그를 본다
```

**해볼 것 세 가지**

| 조작 | 보이는 것 |
| --- | --- |
| ROC에서 해도를 3번 클릭 → `노선 발행` | 계획 항로가 그려지고 배가 그 길로 간다 |
| `원격 조종` 탭 → 침로 270 · DynamicPositioning → 발행 | MASS 화면의 제어권이 **MON(초록) → RC(분홍)** 으로 바뀌고 배가 선회한다 |
| 오른쪽 위 `LINK` 클릭 (무선 차단) | 10초 뒤 ROC가 두절 판정. **30초 뒤 배가 스스로 fallback에 들어가고 제어권이 본선으로 돌아온다** |
| `인증서` 탭 → `정상 인증서 발급` / `위조 인증서 발급` | 정상은 **수락**되어 신뢰저장소에 들어가고, 위조는 **거부**(bad-signature)되며 저장소가 안 늘어난다 (SC-VDE-001) |
| ROC 아래 `정량지표` 패널 | 비인가 수용·인증 성공률·성능 저하가 조작에 따라 실시간으로 바뀐다 |
| 오른쪽 위 `로그 저장` | 지금까지의 세션을 `results/console_<시각>.json`으로 남긴다 (지표 포함) |

끝낼 때는 터미널에서 `Ctrl+C`.

> **판정은 하지 않는다.** 콘솔은 자유 조작이라 미리 정한 기대값이 없다. 합격/불합격이
> 필요하면 상황 A(`scenario_runner`)를 쓴다. 콘솔 로그는 **무슨 일이 있었는지**를
> 남긴다 — 통신 로그·수신 판정·인증서 결과·명령 이력·항적·최종 상태.

> ⚠ **인증서 탭은 응용 계층 검증 시연**이다 — 발급·서명 검증·신뢰저장소 반영을
> GUI 안에서 바로 수행하며 전송 계층을 타지 않는다. 실제 VDE-TER 인증서
> 전송(Data Session)은 링크 계층 미완성(`data_session_enabled=false`)으로
> **현재 미지원**이다.

### 무선 계층까지 통과시키려면

기본은 무선 없이 payload를 직접 넘기는 **시연 모드**다. 실제 VDE-TER Service API를
타게 하려면 (상황 C의 crypto 파이썬 필요):

```bash
python apps/console_server.py --transport software
```

(`vdeter`는 `software`의 이전 이름으로 그대로 통한다. `--transport stage7`은 외부
launcher가 Stage 7 Service를 주입하는 실장비 통합용 seam이라 콘솔 단독으로는 뜨지
않는다 — `apps/console_transport.py`의 `ExternalServiceTransport` 참조.)

명령 반응이 2~3초 걸린다. **느린 것이 정상**이다 — 실제 무선 스택을 지나고 있다는
뜻이다. 위치보고·명령·응용 ACK이 모두 등록된 `payload_format`으로 나간다.

## 상황 A-3 — 정량지표를 측정한다 (설치 불필요) ⭐

프로젝트 목표 3종(**비인가 패킷 수용 0회 · 인증 성공률 99% 이상 · 성능 저하
30% 이하**)을 실제 수치로 낸다. 한 줄이면 끝난다.

```bash
python tools/measure_metrics.py
```

몇 초 뒤 이렇게 나오고 `results/metrics_<시각>.json`에 남는다.

```text
  지표                              측정값          목표  판정
  ----------------------------------------------------------
  비인가 패킷 수용                      0회          0회  통과
  인증 성공률                      100.00%     99% 이상  통과
  성능 저하                           +1.6%     30% 이하  통과

  방어 전(판정 끔): 비인가 8건 중 8건 수용 — 이것이 막으려는 피해다
```

마지막 줄이 핵심이다. **VDE-TER에는 송신자 인증이 없어서**, 방어를 켜지 않으면
ROC가 아닌 국이 보낸 명령도 배가 그대로 따른다(8건 중 8건). 판정을 켜면 0건이
된다. 도구는 그 둘을 한 번에 재서 보여 준다.

무선을 태우려면 (상황 C의 crypto 파이썬 필요, 한 건에 8초쯤 걸려 오래 돈다):

```bash
python tools/measure_metrics.py --transport software --cycles 12
```

콘솔 GUI(상황 A-2)에서도 같은 지표가 ROC 창 아래에 실시간으로 뜬다. 거기서는
`기준 구간` / `보안 구간` 버튼으로 성능 비교 구간을 직접 나눈다.

> 이 수치를 어디까지 믿을 수 있는지 — 특히 **성능 저하는 하한**이라는 점 —
> 는 [`정량지표.md`](정량지표.md)에 적어 뒀다. 보고서에 쓸 때는 그쪽을 함께 본다.

## 상황 C — VDETER 무선 전송까지 시뮬레이션한다 (장비 없이, crypto 필요)

장비 없이 **실제 VDETER 스택(Presentation→Link→PHY→소프트웨어 무선→수신)** 을 통과시켜
본다. 2-2의 crypto 파이썬으로 실행한다(아래 `python`이 그 인터프리터다).

**인증서 응용 검증(참고용)** — 정상 인증서는 검증·저장, 위조 인증서는 링크는 전달하되
응용이 거부. ⚠ 소프트웨어 loopback일 뿐이며, SC-VDE-001의 실제 운영 경로(인증서
Data Session)는 링크 계층 미완성으로 **현재 미지원**이다:

```bash
python apps/cert_loopback_demo.py
```

**노선 종단** — 등록된 `sc_vde.route_control.command` 포맷으로 나른다:

```bash
python apps/route_loopback_demo.py
```

**원격 조종 종단** — 노선과 같은 포맷(Heading·Fallback을 채운 것):

```bash
python apps/control_loopback_demo.py
```

> ⚠️ `sc_vde` 두 포맷은 서명·재전송 보호가 없는 **TEST 전용**이다. 격리된 시험·데모에만
> 쓰고, 실제 조타 장비를 움직이는 데 쓰지 않는다.

**인증서가 실제 VDETER codec 계약을 통과하는지** 검증하는 테스트:

```bash
python tests/test_cert_vdeter_integration.py
```

**응용↔Service API 종단 회귀** — 005·006 명령·ACK 왕복, 중복 적용 방지, 주소 격리:

```bash
python tests/test_mass_roc_link_integration.py
```

> 이것들을 cryptography 없는 파이썬으로 돌리면 "SKIP: cryptography가 없어…"만 뜬다.
> 잘못된 게 아니라, crypto 파이썬으로 돌리라는 뜻이다.

## 상황 D — 실 하드웨어 RF (USRP B210, Stage 7 3노드)

> **승인된 실물 구성은 3노드다** — Raspberry Pi 5 한 대에 B210 **세 대**(ROC ·
> MASS-A · MASS-B)를 USB로 연결하고, B210끼리는 SMA 동축 직결 경로 C1~C6로 잇는
> conducted testbed다(감쇠기·Faraday Cage 불필요 — 링크 팀 구축 완료, 상세:
> `docs/vdeter_interim_report_technical_summary.md` §1·§3, `docs/인수인계.md` §5).
> Stage 7 launcher(`VDETER/apps/stage7_endpoint_launcher.py`)와 소프트웨어 검증
> (전체 PASS)까지 준비됐고, **B210 실물시험 자체는 아직 수행 전**이다 — 하드웨어

### D-1. 장비 연결 — Stage 7 3노드 (링크 팀 구축 완료)

**구성**: Pi 5 한 대에 B210 세 대를 USB 3.0으로 연결하고, 세 B210의 TX/RX·RX2를
SMA 동축 케이블 6개(C1~C6, 단방향 경로 6개)로 서로 직결한다. 케이블 배선표·장비
serial은 `docs/vdeter_interim_report_technical_summary.md` §3에 있다. 안테나는
쓰지 않는다(conducted 전용). 구축·배선은 링크 팀 담당이다.

인식 확인 — Pi에서 세 B210의 serial이 모두 잡히면 정상:

```bash
uhd_find_devices
```

### D-3. ① 간이 벤치 (LEGACY — 참고 기록)

> ⚠ 아래는 구식 2-B210 단방향 벤치 절차의 기록이다. 현재 공식 실물 경로는 ②(D-4)다.
> `VDETER_Link/` 사본은 더 이상 배포되지 않는다.

`rf_normal_cycle.py`가 뽑는 **정상 사이클**은 위치보고 → **항로지시(= SC-VDE-005 메시지)**
→ ACK → 위치보고 네 개다. 즉 이 벤치는 사실상 **노선 교환 메시지를 실 RF로 흘려 복원하는
테스트**다(조종 필드는 항로지시의 확장이라 같은 방식으로 실린다).

**전제(당시)**: 구식 2-B210 감쇠기 직결 결선(`docs/rf_normal_cycle_test.md`) +
`VDETER_Link/` 사본 — 현재는 구할 필요가 없다.

**1) 송신 재료 뽑기** (장비 없이, 송신 PC에서) — 네 메시지 payload와, 송신 콘솔에 그대로
넣을 입력을 출력한다.

```bash
python3 apps/rf_normal_cycle.py payloads
```

**2) (한 PC에 2대인 경우만) 장치 serial 지정** — PC를 나눠 한 대씩 꽂았으면 **건너뛴다**
(각 PC에 B210이 하나뿐이라 그냥 잡힘). 한 PC에 두 대를 꽂은 경우에만
`VDETER_Link/no_error_correction/vdeter_tx.py`의 `tx_dev = 'serial=<A>'`, `vdeter_rx.py`의
`rx_dev = 'serial=<B>'`로 지정한다(D-1의 4)에서 확인한 값).

**3) 수신기(B)를 먼저 켠다** — preamble을 잡을 때마다 `[VDE Message]` 블록에
`Payload (hex): ..`를 찍는다. 이 hex가 우리가 확인할 값이다.

```bash
cd VDETER_Link/no_error_correction
```

```bash
python3 vdeter_rx.py
```

**4) 송신기(A)를 켜고 대화식으로 네 메시지를 순서대로 보낸다** — `config.py`의
`TX_MODE = "interactive"` 확인 후 실행하고, 1)에서 뽑은 입력을 메시지 [1]→[4] 순서로
프롬프트에 붙여넣는다(각 `Repeat count`는 `1`). 한 건 보낼 때마다 수신기(B) 콘솔에
대응하는 `[VDE Message]`가 떠야 한다.

```bash
python3 vdeter_tx.py
```

**5) 복원·필드 일치 확인** — 수신기가 찍은 각 `Payload (hex)`를 복사해 아래로 되돌리면
응용 필드로 복원된다. 1)의 출력과 좌표·침로·항로 필드가 일치하면 그 메시지는 통과다.

```bash
python3 apps/rf_normal_cycle.py decode "<붙여넣은 hex>"
```

**판정**: 네 메시지가 **모두 복원되고 필드가 일치**하면 통과 — 응용↔링크↔RF 경로 통합
성공(정상 대조군 확보). 일부만 복원되면 게인/감쇠/동기 문제, `VPFI가 다릅니다` 거부가
나오면 잡음에서 나온 가짜 preamble이거나 비트가 깨진 것(정상적으로 걸러진 것).

> **그래서 decode + 필드확인이 끝이냐?** — ① 간이 벤치의 목표까지는 그렇다. "우리
> payload가 실 RF를 견디고 반대편에서 필드까지 복원되는가"를 증명하는 스모크 테스트다.
> **세 시나리오를 하나의 방식으로 각각 실 RF로 돌리려면 ② 경로**(D-4)로 간다.

### D-4. ② Stage 7 전체 VDETER 스택 over B210 — 005·006 (실물시험 대기)

**쉽게 말하면**: 상황 C에서 돌린 무선 시뮬레이션(`cert_loopback_demo.py` 등)은, ROC와
MASS 두 무선국을 프로그램 안에 세우고 그 사이를 **가짜 무선**으로 잇는다 — 실제 전파가
아니라 소프트웨어가 "보낸 바이트를 그대로 받은 셈 치는" 흉내다. ② 경로는 **그 가짜 무선
자리에 진짜 B210 무선기를 끼워 넣는 것**뿐이다. 그러면 같은 두 무선국이 이번엔 실제로
전파를 타고 주고받는다.

> **비유.** 앱을 만들 때 처음엔 **가짜 서버(시뮬레이터)** 로 시험하다가, 앱 코드는 그대로
> 두고 접속 대상만 **진짜 서버**로 바꾸는 것과 같다. 여기서 "앱"이 ROC/MASS 로직이고,
> "서버 연결"에 해당하는 게 **무선을 실제로 나르는 밑단**이다. 이 밑단만 소프트웨어 흉내
> → 진짜 B210으로 갈아끼운다.

- **응용 코드(ROC/MASS·codec·브리지)는 한 줄도 안 바뀐다** — 위 계층은 전파가 소프트웨어
  흉내인지 진짜 B210인지 알 필요가 없기 때문이다(§1 그림의 ③ "링크가 전파로 나른다" 부분만
  통째로 교체된다).
- 링크가 ACK·TDMA를 처리하므로 **005·006이 실 RF로** 된다. 인증서(001)는 전체 스택이라도
  **인증서 Data Session이 링크 계층에서 미완성**이라 지금은 제외다
  (`data_session_enabled=false` — 인증서 브랜치 완성 후 재개).
- Stage 7 endpoint 조립·기동은 **링크 팀 launcher**(`VDETER/apps/stage7_endpoint_launcher.py`,
  config `VDETER/configs/stage7/`)가 맡는다. 응용(MASS/ROC) 연결은
  `apps/console_transport.py`의 **`ExternalServiceTransport` 주입 seam**을 쓴다 —
  공식 in-process 연결점은 `build_stage7_b210_endpoint(..., application_sink=...)`뿐이고,
  별도 프로세스 launcher에 접속하는 응용 RPC는 공개 API에 없다(가이드 §15). 그
  cross-process 연결 방식 확정은 링크 팀과의 남은 통합 항목이다.
- 우리 loopback 데모·회귀(`tests/test_mass_roc_link_integration.py`)가 그 **직전
  단계(소프트웨어 무선까지)를 이미 증명**해 뒀다.

### D-5. USRP 몇 대? (현재 기준: 3대)

- **승인 구성은 3대**다 — ROC·MASS-A·MASS-B 각 station에 B210 1대씩, 단일 Pi 5,
  SMA 직결 C1~C6 conducted. VDETER는 이미 **3국을 소프트웨어로** 돌리고 있고
  (`build_stage5_software_group`), 3-endpoint 통합 시험
  (`VDETER/tests/integration/test_mac_three_endpoint.py`)도 있다. MAC/TDMA가 공유
  채널에서 여러 국을 조율한다.
- 세 번째 국(MASS-B)은 **주소 격리 검증**(ROC→MASS-A 명령이 MASS-B에 적용되지 않음)과
  필요 시 MASS-A↔MASS-B 경로 실험에 쓴다. 공격 실험(위조·재전송) station으로도 쓸 수 있다.
- 구식 ① 벤치는 2대 전용(단방향 1링크)이었다 — LEGACY, D-3 참조.

## 3. 각 시나리오가 실제로 하는 일

### ① SC-VDE-001 인증서 송수신 (현재 미지원)

ROC가 X.509 공개키 인증서를 만들어 **R1027 Certificate Report 본문**으로 감싸 MASS에
보낸다. MASS는 **서명을 신뢰 앵커(CA)로 검증**하고 통과한 것만 신뢰 저장소에 넣는다.
위조·만료 인증서는 거부하고 저장소를 건드리지 않는다. → *"링크는 신뢰를 판정하지 않고,
응용이 판정한다"* 를 보여준다.

> ⚠ 운영 실행은 **현재 미지원**이다 — 실제 인증서 전달이 쓰는 VDE-TER **Data
> Session이 링크 계층에서 미완성**(`data_session_enabled=false`)이기 때문이다. 응용
> 코드·코덱·단위시험은 보존되어 있고, 러너에서 고르면 미지원 안내가 나온다.

### ② SC-VDE-005 S-421 노선 계획

ROC가 항로(웨이포인트·계획속도·leg 기하)를 **압축 비트 형식**으로 실어 보낸다. MASS가
받아 풀고 검증 결과를 **S-421 상태코드 ACK**(4=Acknowledged 등)로 돌려준다.

### ③ SC-VDE-006 원격 조종

**노선이 이미 교환된 상황을 전제**로, ROC가 조종 명령(목표 heading·fallback 상태·속도
조정)을 보낸다. 노선지시 메시지의 확장으로 실리며, 압축 코덱을 왕복해도 heading·
fallback·SOG가 보존되는지 확인하고 ACK를 돌려준다.

## 4. 로그·분석은 어떻게 남는가

- **기록**(`common/observe/scenario_log.py`) — 송수신 시각·방향·종류·검증 결과·ACK
  상태를 시간순으로 남긴다. JSON으로 직렬화된다.

  합격/불합격, 지연(min/max/mean), 재전송 횟수를 낸다.
- 실행할 때마다 콘솔에 판정이 뜨고, `results/SC-VDE-00X_<시각>.json`에 저장된다
  (`--no-save`로 끌 수 있음).

> ⚠️ 이 두 파일은 **라이브러리**다. `python3 common/observe/scenario_analysis.py`처럼
> 직접 실행하면 자체 점검용 예시만 보여준다(실제 시나리오 로그가 아님). 로그·분석
> 자체가 규격대로 도는지 확인하려면 `python3 tests/test_scenario_log.py`, 실제 시나리오
> 로그·판정은 상황 A의 러너(`python3 apps/scenario_runner.py`)로 본다.
