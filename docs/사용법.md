# MASS/ROC 시나리오 — 동작 원리와 사용법

이 문서는 **무엇이 어떻게 동작하는지**와 **상황별로 어떤 명령을 순서대로 치면 되는지**를
정리한다. 터미널만 있으면 따라 할 수 있게 썼다.

---

## 1. 큰 그림 (먼저 이것만)

```
ROC(육상 관제)                                            MASS(선박)
  RocAgent                                                 MassAgent
    │ ① 보낼 데이터를 만든다                                  ↑ ④ 받아서 검증·반영하고
    │   (인증서 / 노선 / 조종 명령)                            │    ACK를 돌려준다
    ▼ ② payload(바이트)로 바꾼다 (PI: codec / bridge)         │
    └────── ③ VDETER 링크가 전파로 나른다 (팀원 담당) ─────────┘
```

- **ROC/MASS(우리 코드)** — 무슨 데이터를 주고받을지 만들고 검증한다. 전파가 어떻게
  나가는지는 모른다.
- **VDETER(팀원 코드)** — 그 바이트를 실제로 실어 나른다.
- **시나리오 3개** — ① X.509 인증서 송수신 ② S-421 노선 계획 교환 ③ MASS-ROC 원격 조종.
- **로그·분석** — 시나리오를 돌릴 때마다 무슨 일이 있었는지 시간순으로 기록하고,
  규격대로 됐는지 **합격/불합격**을 판정해 `results/`에 저장한다.

**핵심**: 장비(USRP B210)가 없어도 소프트웨어만으로 시나리오 전체를 돌리고, VDETER
전송까지 시뮬레이션할 수 있다. 장비는 맨 마지막 실 RF 검증에만 필요하다.

## 상황 A — 시나리오를 골라 돌려본다 (장비·설치 불필요) ⭐

가장 자주 쓰는 방법. **대화형 메뉴**로 고르면 바로 실행된다.

```bash
python3 apps/scenario_runner.py
```

그러면 이런 메뉴가 뜬다:

```
=== MASS/ROC 시나리오 재현 (대화형) ===
  1) SC-VDE-001  X.509 인증서 송수신
  2) SC-VDE-005  S-421 노선 계획 교환
  3) SC-VDE-006  MASS-ROC 원격 조종
  a) 전체 실행
  q) 종료

선택 >
```

- **번호(1·2·3)** 또는 **시나리오 ID**를 입력하면 즉시 실행하고, 시간순 타임라인 +
  합격/불합격 판정을 보여준 뒤 **다시 메뉴로 돌아온다.**
- **`a`** = 세 시나리오 전체 실행, **`q`** = 종료.
- 실행할 때마다 로그가 `results/`에 저장된다.

### 명령을 직접 치고 싶으면 (스크립트·자동화용)

```bash
python3 apps/scenario_runner.py list
```

```bash
python3 apps/scenario_runner.py run SC-VDE-001
```

옵션: `--json`(기계용 JSON 출력) · `--no-save`(로그 파일 안 남김) · `--now <숫자>`(기준 시각 고정, 재현용).

### 결과 읽는 법

- **타임라인**: `+0.30s  ROC->MASS  send  조종 데이터 …` 처럼 누가 언제 무엇을 했는지.
- **판정**: `[PASS] ack-status …`, 맨 위에 `— 합격 / 불합격`.
- **파일**: `results/SC-VDE-00X_<시각>.json` 에 전체 로그가 저장된다.

```bash
ls results
```

## 상황 C — VDETER 무선 전송까지 시뮬레이션한다 (장비 없이, crypto 필요)

장비 없이 **실제 VDETER 스택(Presentation→Link→PHY→소프트웨어 무선→수신)** 을 통과시켜
본다. 2-2의 venv가 필요하고, 실행은 **`.venv-crypto/bin/python`** 으로 한다.

**인증서 종단** — 정상 인증서는 검증·저장, 위조 인증서는 링크는 전달하되 응용이 거부:

```bash
.venv-crypto/bin/python apps/cert_loopback_demo.py
```

**노선 종단** — ⚠️ 노선용 운영 포맷이 아직 없어 시험용 opaque 포맷으로 나른다:

```bash
.venv-crypto/bin/python apps/route_loopback_demo.py
```

**원격 조종 종단**:

```bash
.venv-crypto/bin/python apps/control_loopback_demo.py
```

**인증서가 실제 VDETER codec 계약을 통과하는지** 검증하는 테스트:

```bash
.venv-crypto/bin/python tests/test_cert_vdeter_integration.py
```

> 이 세 개를 그냥 `python3`(시스템)로 돌리면 "SKIP: cryptography가 없어…"만 뜬다.
> 잘못된 게 아니라, venv 파이썬으로 돌리라는 뜻이다.

## 상황 D — 실 하드웨어 RF (USRP B210)

> **현재 감쇠기(attenuator)가 없어 아직 못 한다.** 안테나 직결은 수신단을 손상시키고,
> 공중 실험은 Faraday Cage가 필요하다(`references/VDE-TER_Faraday_Cage_구축계획서.html`).
> 아래는 **장비 연결부터 시나리오별 실행까지** 조건이 갖춰졌을 때의 순서다.

### D-0. RF 경로가 두 가지다

| 경로                                                               | 무엇                                         | 실을 수 있는 것                               | 상태              |
| ---------------------------------------------------------------- | ------------------------------------------ | --------------------------------------- | --------------- |
| **① 간이 벤치** (`rf_normal_cycle.py` + `VDETER_Link`)               | 단일 슬롯 Type 92/93로 payload 하나씩 전파에 실어 복원 확인 | 작은 메시지(노선·조종 ~32B). **인증서(~300B+)는 불가** | 감쇠기 대기          |
| **② 전체 VDETER 스택 over B210** (상황 C loopback의 무선 매체만 실 B210으로 교체) | Presentation~PHY 전체를 실 무선으로. 분할·재조립·ACK 포함 | **3개 시나리오 전부**(인증서 포함)                  | 팀원 배선 + 하드웨어 대기 |

### D-1. 장비 연결 — 모든 RF 실험 공통 (순차)

**구성**: **PC 2대**를 쓰고, 각 PC에 **B210을 한 대씩** 연결한다 — 송신 PC에 B210-A,
수신 PC에 B210-B. 케이블로 잇는 건 **두 무선기(B210) 사이**이지 PC끼리가 아니다. 전원을
켜기 전에 **결선부터** 하고, **안테나는 절대 쓰지 않는다** — 감쇠기 없이 전파를 직접
받으면 수신단이 손상된다.

1. **각 PC에 B210 한 대씩 연결** — 송신 PC에 B210-A, 수신 PC에 B210-B를 각각 **USB 3.0**
   케이블로 꽂는다. (한 PC에 두 대를 꽂는 구성이 아니다.)

2. **송신기 A의 `TX/RX` 포트에 30 dB 감쇠기를 직접 체결**한다.

3. **감쇠기 반대편 ─ 동축 케이블 ─ 수신기 B의 `RX2` 포트**로 잇는다. 두 B210을 잇는
   유일한 경로가 이 케이블이다.
   
   ```text
   [송신 PC] ─USB─ B210-A [TX/RX] ── 30dB 감쇠기 ── 동축 ── [RX2] B210-B ─USB─ [수신 PC]
   ```

4. **인식 확인** — 각 PC에서 자기 B210이 잡히는지 본다. PC마다 serial이 하나씩 나오면 정상.
   
   ```bash
   uhd_find_devices
   ```

> **serial을 코드에 박아야 하나?** — PC를 나눠 **한 대씩** 꽂았으면 각 PC에 B210이 하나뿐
> 이라 그냥 잡히므로 **필요 없다.** 드물게 한 PC에 두 대를 꽂은 경우에만 UHD가 어느 걸
> 잡을지 모호해져 코드에 serial을 지정한다(D-3 참조). 3대 이상이면 동축 직결이 안 되고 RF
> combiner/splitter나 Faraday Cage가 필요하다(D-5).

### D-2. 시나리오별 RF 경로 — 어느 쪽으로, 지금 되는가

| 시나리오                 | payload 크기 | ① 간이 벤치            | ② 전체 스택 | 지금 상태        |
| -------------------- | ---------- |:------------------:|:-------:| ------------ |
| **SC-VDE-001 인증서**   | ~300 B+    | ✗ (한 슬롯 초과, 분할 필요) | ✅       | ② 배선 대기      |
| **SC-VDE-005 노선**    | ~32 B      | ✅                  | ✅       | ① 가능(감쇠기 대기) |
| **SC-VDE-006 원격 조종** | ~32 B      | ✅                  | ✅       | ① 가능(감쇠기 대기) |

- **인증서(001)** 는 한 슬롯에 안 들어가 **② 전체 스택으로만** 실 RF가 된다(D-4).
- **노선(005)·조종(006)** 은 작아서 **① 간이 벤치**로 지금 형태로도 전파에 실을 수 있다
  (D-3). 세 시나리오를 하나의 방식으로 각각 돌리는 완전한 형태는 ②(D-4)다.

### D-3. ① 간이 벤치 — 노선·조종 메시지를 실 RF로 (감쇠기 있으면 지금 가능)

`rf_normal_cycle.py`가 뽑는 **정상 사이클**은 위치보고 → **항로지시(= SC-VDE-005 메시지)**
→ ACK → 위치보고 네 개다. 즉 이 벤치는 사실상 **노선 교환 메시지를 실 RF로 흘려 복원하는
테스트**다(조종 필드는 항로지시의 확장이라 같은 방식으로 실린다).

**전제**: D-1 결선 완료 + `VDETER_Link/` 사본(gitignore, 링크 팀원에게 받기).

**1) 송신 재료 뽑기** (장비 없이, 송신 PC에서) — 네 메시지 payload와, 송신 콘솔에 그대로
넣을 입력을 출력한다.

```bash
python3 apps/rf_normal_cycle.py payloads
```

**2) (한 PC에 2대인 경우만) 장치 serial 지정** — PC를 나눠 한 대씩 꽂았으면 **건너뛴다**
(각 PC에 B210이 하나뿐이라 그냥 잡힘). 한 PC에 두 대를 꽂은 경우에만
`VDETER_Link/no_error_correction/vdeter_tx.py`의 `tx_dev = 'serial=<A>'`, `vdeter_rx.py`의
`rx_dev = 'serial=<B>'`로 지정한다(D-1의 4)에서 확인한 값).

**3) 수신기(B)를 먼저 켠다** — preamble을 잡을 때마다 `[VDE Message]` 블록에
`Payload (hex): ..`를 찍는다. 이 hex가 우리가 확인할 값이다.

```bash
cd VDETER_Link/no_error_correction
```

```bash
python3 vdeter_rx.py
```

**4) 송신기(A)를 켜고 대화식으로 네 메시지를 순서대로 보낸다** — `config.py`의
`TX_MODE = "interactive"` 확인 후 실행하고, 1)에서 뽑은 입력을 메시지 [1]→[4] 순서로
프롬프트에 붙여넣는다(각 `Repeat count`는 `1`). 한 건 보낼 때마다 수신기(B) 콘솔에
대응하는 `[VDE Message]`가 떠야 한다.

```bash
python3 vdeter_tx.py
```

**5) 복원·필드 일치 확인** — 수신기가 찍은 각 `Payload (hex)`를 복사해 아래로 되돌리면
응용 필드로 복원된다. 1)의 출력과 좌표·침로·항로 필드가 일치하면 그 메시지는 통과다.

```bash
python3 apps/rf_normal_cycle.py decode "<붙여넣은 hex>"
```

**판정**: 네 메시지가 **모두 복원되고 필드가 일치**하면 통과 — 응용↔링크↔RF 경로 통합
성공(정상 대조군 확보). 일부만 복원되면 게인/감쇠/동기 문제, `VPFI가 다릅니다` 거부가
나오면 잡음에서 나온 가짜 preamble이거나 비트가 깨진 것(정상적으로 걸러진 것).

> **그래서 decode + 필드확인이 끝이냐?** — ① 간이 벤치의 목표까지는 그렇다. "우리
> payload가 실 RF를 견디고 반대편에서 필드까지 복원되는가"를 증명하는 스모크 테스트다.
> **세 시나리오를 하나의 방식으로 각각 실 RF로 돌리려면 ② 경로**(D-4)로 간다.

### D-4. ② 전체 VDETER 스택 over B210 — 3 시나리오 전부 (팀원 배선 후)

**쉽게 말하면**: 상황 C에서 돌린 무선 시뮬레이션(`cert_loopback_demo.py` 등)은, ROC와
MASS 두 무선국을 프로그램 안에 세우고 그 사이를 **가짜 무선**으로 잇는다 — 실제 전파가
아니라 소프트웨어가 "보낸 바이트를 그대로 받은 셈 치는" 흉내다. ② 경로는 **그 가짜 무선
자리에 진짜 B210 무선기를 끼워 넣는 것**뿐이다. 그러면 같은 두 무선국이 이번엔 실제로
전파를 타고 주고받는다.

> **비유.** 앱을 만들 때 처음엔 **가짜 서버(시뮬레이터)** 로 시험하다가, 앱 코드는 그대로
> 두고 접속 대상만 **진짜 서버**로 바꾸는 것과 같다. 여기서 "앱"이 ROC/MASS 로직이고,
> "서버 연결"에 해당하는 게 **무선을 실제로 나르는 밑단**이다. 이 밑단만 소프트웨어 흉내
> → 진짜 B210으로 갈아끼운다.

- **응용 코드(ROC/MASS·codec·브리지)는 한 줄도 안 바뀐다** — 위 계층은 전파가 소프트웨어
  흉내인지 진짜 B210인지 알 필요가 없기 때문이다(§1 그림의 ③ "링크가 전파로 나른다" 부분만
  통째로 교체된다).
- 링크가 분할·재조립·ACK·TDMA를 처리하므로 **인증서 포함 3개 시나리오 전부** 실 RF로 된다
  (간이 벤치 ①은 단일 슬롯이라 인증서 불가).
- 이 "가짜 무선 → 진짜 B210" 교체는 **무선을 담당하는 부품 하나를 갈아끼우는 것**이지만,
  그 부품이 실제 USRP 장비를 여는 부분이라 **팀원(링크 담당)의 영역**이다
  (`VDETER/src/vdeter/radio/b210/`의 실장비 어댑터). 하드웨어·감쇠기가 갖춰지면 함께
  진행한다. 우리 loopback 데모가 그 **직전 단계(가짜 무선까지)를 이미 증명**해 뒀다.
- 실행은 별도 스크립트가 아니라 **상황 C의 데모/러너를 진짜 B210 위에서 그대로 재생**하는
  형태가 된다(`run SC-VDE-001/005/006`이 소프트웨어 대신 실 무선으로 나감).

### D-5. USRP 몇 대? (2대 vs 3대)

| 대수     | 토폴로지 예                           | ① 간이 벤치            | ② 전체 스택           |
|:------:| -------------------------------- |:------------------:|:-----------------:|
| **2대** | 육상(ROC) ↔ 선박(MASS) 1링크           | ✅ (A=송신, B=수신)     | ✅                 |
| **3대** | 육상 + 선박 2척, 또는 육상 + 선박 + **공격자** | ✗ (도구가 단방향 1링크 전용) | ✅ (VDETER가 3국 지원) |

- **② 전체 스택은 3대도 그대로** 확장된다. VDETER는 이미 **3국(ROC·MASS_A·MASS_B)** 을
  소프트웨어로 돌리고 있고(`build_stage5_software_group`), 3-endpoint 통합 시험
  (`VDETER/tests/integration/test_mac_three_endpoint.py`)도 있다. 하드웨어로 가면 **각
  station = B210 1대**이고, MAC/TDMA가 공유 채널에서 여러 국을 조율한다. 3번째 국은
  **공격자 station**으로 두면 위조·재전송 공격 실험(SC-VDE 공격군)에 바로 쓸 수 있다.
- **① 간이 벤치는 2대 전용**이다(A=송신 전용, B=수신 전용의 단방향 1링크). 3대를 쓰려면
  플로우그래프를 다중국용으로 확장해야 하므로, 3대 실험은 ② 경로로 가는 게 맞다.
- **결선 차이**: 2대는 `동축 + 30dB 감쇠기` 직결이면 되지만, **3대 이상이 같은 RF 매체를
  공유**하려면 RF combiner/splitter 또는 Faraday Cage가 필요하다(동축 직결은 점대점이라
  3국을 못 묶는다).

## 3. 각 시나리오가 실제로 하는 일

### ① SC-VDE-001 인증서 송수신

ROC가 X.509 공개키 인증서를 만들어 **R1027 Certificate Report 본문**으로 감싸 MASS에
보낸다. MASS는 **서명을 신뢰 앵커(CA)로 검증**하고 통과한 것만 신뢰 저장소에 넣는다.
위조·만료 인증서는 거부하고 저장소를 건드리지 않는다. → *"링크는 신뢰를 판정하지 않고,
응용이 판정한다"* 를 보여준다.

### ② SC-VDE-005 S-421 노선 계획

ROC가 항로(웨이포인트·계획속도·leg 기하)를 **압축 비트 형식**으로 실어 보낸다. MASS가
받아 풀고 검증 결과를 **S-421 상태코드 ACK**(4=Acknowledged 등)로 돌려준다.

### ③ SC-VDE-006 원격 조종

**노선이 이미 교환된 상황을 전제**로, ROC가 조종 명령(목표 heading·fallback 상태·속도
조정)을 보낸다. 노선지시 메시지의 확장으로 실리며, 압축 코덱을 왕복해도 heading·
fallback·SOG가 보존되는지 확인하고 ACK를 돌려준다.

## 4. 로그·분석은 어떻게 남는가

- **기록**(`common/observe/scenario_log.py`) — 송수신 시각·방향·종류·검증 결과·ACK
  상태를 시간순으로 남긴다. JSON으로 직렬화된다.
- **분석**(`common/observe/scenario_analysis.py`) — 기록을 기대치와 대조해
  합격/불합격, 지연(min/max/mean), 재전송 횟수를 낸다.
- 실행할 때마다 콘솔에 판정이 뜨고, `results/SC-VDE-00X_<시각>.json`에 저장된다
  (`--no-save`로 끌 수 있음).

> ⚠️ 이 두 파일은 **라이브러리**다. `python3 common/observe/scenario_analysis.py`처럼
> 직접 실행하면 자체 점검용 예시만 보여준다(실제 시나리오 로그가 아님). 로그·분석
> 자체가 규격대로 도는지 확인하려면 `python3 tests/test_scenario_log.py`, 실제 시나리오
> 로그·판정은 상황 A의 러너(`python3 apps/scenario_runner.py`)로 본다.
