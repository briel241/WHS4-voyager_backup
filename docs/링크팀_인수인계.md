# 링크 팀 인수인계 — 실장비(Stage 7) 실행에 필요한 것

> 응용 계층(MASS/ROC) 쪽에서 링크 팀에 넘기는 것과, 실장비 실행 전에 함께
> 확인해야 하는 것을 정리한다. 작성 시점 기준은 `origin/main` `2036cb2`
> (Stage 7 B210 system 머지)다.

---

## 0. 요약 — 세 가지

| #   | 항목                                        | 성격                       |
|:---:| ----------------------------------------- | ------------------------ |
| 1   | **실제 payload fixture 5종** 넘김              | 우리가 만들어 뒀다. 쓸지 결정만 하면 된다 |
| 2   | **인증서가 400 B를 넘는다** — 411~413 B (요청하신 확인) | **보고**                   |
| 3   | **인증서 크기가 실행마다 변동**한다 (±3 B)              | 고정 크기 가정이면 위험            |

이 밖에 응용 계층에서 링크 팀에 요청할 미결 사항은 **없다**. payload_format
등록(`sc_vde.*`)과 Stage 7 launcher는 모두 확보됐고, 우리 시험은 전부 통과 중이다.

## 1. 실제 payload fixture — 넘기는 것

### 왜 필요한가

Stage 7 Scenario Controller는 `--fixtures-dir`의 JSON을 읽어 endpoint에게
`VdeService.submit()`을 시킨다. 현재 `prepare_stage7_run_configs.py`가 만드는
fixture는 이렇다.

```python
"payload_format": "test.stage0.opaque",
"payload_base64": base64.b64encode(payload_bytes(length, seed)),
```

**크기와 전송 유형만 재현**한다. 단편화·ACK·방향 검증에는 충분하지만,
**우리 실제 메시지가 실장비를 통과하는지는 확인되지 않는다.** 등록된
`sc_vde.*`·`x509.certificate_report` codec을 타지 않기 때문이다.

### 우리가 만들어 둔 것

```bash
python tools/make_stage7_fixtures.py --out results/stage7-fixtures
```

같은 JSON 형식에 **실제 payload와 등록된 payload_format**을 넣어 5종을 낸다.

| fixture                              | 방향         | application | payload_format                 | ACK |
| ------------------------------------ | ---------- | -----------:| ------------------------------ |:---:|
| `submit-sc-vde-005-route.json`       | ROC→MASS-A | 29 B        | `sc_vde.route_control.command` | 요구  |
| `submit-sc-vde-006-control.json`     | ROC→MASS-A | 10 B        | `sc_vde.route_control.command` | 요구  |
| `submit-sc-vde-006-ack.json`         | MASS-A→ROC | 3 B         | `sc_vde.route_control.ack`     | 불요  |
| `submit-sc-vde-position.json`        | MASS-A→ROC | 14 B        | `sc_vde.position_report`       | 불요  |
| `submit-sc-vde-001-certificate.json` | ROC→MASS-A | **~412 B**  | `x509.certificate_report`      | 요구  |

**검증 완료** — 5종 모두 실 VDETER codec을 `encode`→`decode` 왕복해 바이트가
일치한다. wire prefix도 확인했다 (`ff 7f 02` / `ff 7f 03` / `ff 7f 01` / `00 01`).

`start-*.json`과 `stop.json`은 링크 팀 생성기 것을 그대로 쓴다. **`submit-*.json`만
교체**하면 된다.

### 현재 fixture와의 대응

| 링크 팀 현재                               | 우리 대응                            | 비고                          |
| ------------------------------------- | -------------------------------- | --------------------------- |
| `short-roc-to-a` 29 B                 | `sc-vde-005-route` 29 B          | **크기 정확히 일치**               |
| `data-roc-to-a` 353 B                 | `sc-vde-001-certificate` ~412 B  | **정본 구성으로 맞췄다** — 아래 §2·§3  |
| `short-b-to-roc-noack` 30 B (MASS-B발) | `sc-vde-position` 14 B (MASS-A발) | 크기·송신자 다름                   |
| `timeout-unknown-dest`                | (해당 없음 — 링크 계층 시험)               | 유지                          |
| —                                     | `sc-vde-006-control` 10 B        | **없던 유형** — 최소 크기 addressed |
| —                                     | `sc-vde-006-ack` 3 B             | **없던 유형** — MASS→ROC 최소     |

`prepare_stage7_run_configs.py`를 고쳐 한곳에서 관리할지, 우리 fixture를 그대로
쓸지는 정해 주면 맞추겠다.

## 2. 인증서가 400 B를 넘는다 — 요청하신 확인 결과 ⚠️

**넘는다.** SC-VDE-001 인증서의 application payload는 **411~413 B**다
(`apps/scenario_runner.py` 정본 기준, 표준 ECDSA 백엔드, 40회 표본).

### 크기를 좌우하는 것 — X.509 확장 필드

| 구성                  | application |
| ------------------- | -----------:|
| 확장 없음               | 303 B       |
| + `mass_id`         | 329 B       |
| + `roc_id`          | 352 B       |
| + `mmsi`            | 380 B       |
| **+ `imo` (정본 구성)** | **~405 B**  |

확장 하나가 **25~28 B**씩 더한다. 정본 시나리오는 넷을 모두 넣는다 —
선박 인증서에 필요한 식별 정보이기 때문이다.

### 더 커질 수 있는 경우

| 상정                                     | 크기         |
| -------------------------------------- | ----------:|
| 정본 시나리오                                | 411~413 B  |
| 식별자가 길어지면 (예: `MASS-KR-BUSAN-01`)      | 440~442 B  |
| **응용 계층 상한 (`MAX_CERTIFICATE_BYTES`)** | **1024 B** |

CRL을 동봉하거나 인증서를 여러 건 담으면(`build_report`는 다중 entry를 받는다)
더 커진다. **Data Session 설계 시 400 B가 아니라 1024 B를 상한으로 봐 주면**
이후 확장에도 안전하다.

### 다른 메시지는 여유가 있다

노선·조종·ACK·위치보고는 **3~164 B**다(웨이포인트 16개 기준 164 B). Short Data
범위이므로 Data Session이 필요 없다.

> Data Session 구현이 완료되어 임시 `data_session_enabled` 차단 설정은 제거됐다.
> 인증서 전송은 Link가 분할·재조립·ACK를 처리한다.

## 3. 인증서 크기가 고정이 아니다 ⚠️

`data-roc-to-a` fixture가 353 B로 고정돼 있고 커밋 메시지에 `(2 fragments)`로
적혀 있다. 그런데 **같은 구성에서도 실행마다 ±3 B 흔들린다.**

```
411 B / 412 B / 413 B  ...  (같은 코드, 다른 실행)
```

ECDSA 서명의 DER 인코딩 길이가 가변이기 때문이다 — `r`·`s` 값에 따라 선행
0x00 패딩이 붙거나 빠진다.

### 확인하고 싶은 것

- fragment 경계가 이 변동 폭 안에 있지 않은지
- 405~445 B 범위 전체에서 같은 fragment 수가 나오는지

경계에 걸리면 "어제는 2 fragment였는데 오늘은 3"이 되어 재현이 흔들린다.
