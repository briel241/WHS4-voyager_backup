# MASS/ROC 응용 계층 — 인수인계

---

## 1. 브랜치에 올린 거?

- `feat/mass-roc-app` 브랜치에 **MASS(선박) ↔ ROC(육상) 응용 계층**을 올림.
- 원래 비어 있던 `MASS/`·`ROC/` 폴더를 실제 구현으로 채웠고, 두 쪽이 함께 쓰는 코드는 `common/`에 둠.
- 커밋·푸시·PR까지 완료.
- 링크·PHY 계층(`VDETER/`)은 안건드림.

---

## 2. 폴더 구조

```
common/   MASS·ROC 공유 (핵심)
  messages/   응용 메시지 7종 + registry
  codec.py    PI — 메시지 ↔ payload 바이트 변환
  coordinates.py bitfield.py navigation.py config.py
  outbound.py 송신 요청 / service.py API 어댑터
  security/   ECDSA·HMAC 서명 / observe/ 관찰 도구
MASS/     mass_agent.py   선박 행위자
ROC/      roc_agent.py    육상 행위자
docs/     시나리오·요구사항·설계 문서
tests/    시험 6종
apps/     실행 데모 3종
VDETER/   링크·PHY (건드리지 않음)
```

---

## 3. 핵심 내용

- MASS/ROC는 **payload(바이트)** 를 주고받음. 링크·전파는 `VDETER/`가 처리하고, 응용은 그 안을 모름.
- **PI(`codec.py`)** 가 응용 데이터 ↔ payload를 변환함. 봉투 구조:
  `[ VPFI 16bit | Message ID 8bit | 본문 | byte 패딩 ]`
- **메시지 7종**:
  위치보고 · 항로지시 · 응답(ACK) · AIS 인증값 · 항행경보 · 환경정보 · 기상관측
- 필드는 **실제 표준을 차용**했음 (AIS/IFM · S-124 · WMO BUFR · S-104/411/412).
  표준에 없는 것(자율운항 모드 등)만 직접 정의했고, 코드 주석에 그렇게 표시해뒀음.
- **행위자 둘**:
  - `MassAgent` — 항로 따라 움직이고, 위치보고 내보내고, 받은 항로·경보를 검증·반영함.
  - `RocAgent` — 항로 지시·AIS 인증값·항행경보를 만들어 내보냄.
  - 둘 다 `Outbound`(송신 요청)만 만들고, 링크에 어떻게 실리는지는 모름.

| 상태           | 시나리오/메시지                                   |
| ------------ | ------------------------------------------ |
| **VDETER 종단 연동** | **인증서(SC-VDE-001)** — 소프트웨어 무선 loopback으로 ROC→MASS 인증서가 실 VDETER 스택 전체를 왕복(COMPLETED·byte 일치)하고 응용이 검증·저장. 위조 인증서는 링크는 전달하되 응용이 거부. `apps/cert_loopback_demo.py` |
| **확정 3종 재현·로그** | 인터페이스(`apps/scenario_runner.py`)가 확정 3개 시나리오를 선택·실행·판정: `SC-VDE-001`(인증서) · `SC-VDE-005`(S-421 노선) · `SC-VDE-006`(원격 조종). 원격 조종은 노선 하위 시나리오로, 조종 필드(heading·fallback·SOG)가 압축 코덱을 왕복함을 확인 |
| **행위자까지 구현** | 위치보고·항로(정상 동작) · AIS 인증값 · 항행경보(방송→반영)     |
| **메시지만 구현**  | 환경정보 · 기상관측 (행위자 연결 안 됨)                   |
| **설계만**      | 제어권 전환 · 비상 개입 · 브로드캐스트 인증(ECDSA vs TESLA) |

## 6. 해야 할 일

1. **`VDETER/` 연동** — 팀원이 API 가이드(`docs/vdeter_mass_roc_api_guide.md`)를 냈고,
   **인증서(SC-VDE-001) 경로는 실 연동·검증까지 끝냈음.**
   - **끝난 것 (인증서)**: `common/vdeter_bridge.py`가 우리 `Outbound`를 VDETER
     `SubmitTransferRequest`(`Addressed`/`StationId`/`PayloadFormat`)로 바꾸고, 수신
     `ReceivedApplicationData`를 응용이 다룰 `Inbound`로 폄. 인증서 payload는
     `common/messages/certificate_report.py`가 R1027 Certificate Report 본문으로 만들며,
     **실 VDETER `CertificateReportCodec` 왕복을 통과**함(`tests/test_cert_vdeter_integration.py`).
     송신/수신/검증/저장·위조·만료 거부까지 확인. `cert_flow.roc_issue_certificate_report`
     / `mass_receive_certificate_report`가 흐름임. **표준 백엔드(cryptography) 필수** —
     VDETER codec이 진짜 X.509 DER 구조를 검증하기 때문.
   - **종단 왕복 확인**: `apps/cert_loopback_demo.py`가 VDETER의 소프트웨어 무선 그룹
     (`build_stage5_software_group`, tests/support 하네스)으로 하드웨어·팀원 launcher
     없이 ROC→MASS 인증서를 실제로 보내 COMPLETED·byte 일치·검증·저장까지 재현함.
     위조 인증서는 링크는 전달하되 응용 검증이 거부(신뢰저장소 불변) — SC-VDE-001
     위협 모델 그대로.
   - 앱은 `vdeter.service.VdeService`의 `start/submit/status/cancel/stop`만 호출함.
     MASS=`SHIP`, ROC=`CONTROL`. payload는 **VDE 헤더 없는 순수 bytes**. 운영에서
     `VdeService` 구현은 launcher가 주입함(앱이 직접 안 만듦).
   - **아직 남은 것**: 우리 codec의 16-bit VPFI 봉투 제거(계열 A 메시지용) · AIS 인증값
     (SC-VDE-003)도 같은 브리지로 붙이면 됨(포맷 지원됨) · 실 endpoint 왕복(launcher 필요).
   - **막혀 있는 것**: 항로(SC-VDE-005)·항행경보(009)·환경·기상은 **VDETER registry에 format이
     없어 불가**. 링크 팀이 wire 식별자·codec을 추가해줘야 함(위 브리지에 data_type 매핑만 추가).
   - **MASS 발신 broadcast 미지원** — 위치보고(MASS→broadcast)는 현재 VDETER로 못 보냄.
2. **시나리오 2개 선별** — 개발 대상 3개 중 인증서(SC-VDE-001)만 확정. 나머지 2개는
   서비스 카탈로그에서 고르고, 그중 하나(MASS 조작 데이터)는 멘토 자문 예정.
3. **Route Plan 기밀성** — S-421 항로는 노출되면 표적화 위험이 있어 암호화(SECOM)가
   필요할 수 있음. 인증만 할지, 암호화까지 할지 범위 결정 필요.
4. **환경·기상 메시지 행위자 연결** — 경보(§항행경보)와 같은 패턴으로 붙이면 됨.
5. **RF 실험 환경** — 감쇠기 없이 공중 실험하려면 Faraday Cage가 필요함. 팀 계획서:
   `references/VDE-TER_Faraday_Cage_구축계획서.html`.
