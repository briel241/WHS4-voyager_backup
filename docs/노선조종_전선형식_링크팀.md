# 노선(SC-VDE-005)·원격조종(SC-VDE-006) 전선 형식 — 링크 팀 전달용

> 링크 팀이 노선/조종 payload를 **인식·검증하는 codec + payload_format**을 만들 수 있도록,
> 실제 응용이 생성하는 **전선 비트 레이아웃**을 정확히 정리한다. 인증서의
> `x509.certificate_report` codec에 대응하는 route/control 버전을 만드는 것이 목표다.
>
> 근거 코드: `common/messages/route_instruction.py`(노선·조종), `common/messages/application_ack.py`(ACK),
> `common/codec.py`(봉투), `common/coordinates.py`(좌표).

---

## 0. 요약

- **노선(005)과 조종(006)은 같은 메시지**(Message ID 2, `Route Instruction`)를 쓴다.
  조종은 여기에 `heading_setpoint`·`fallback_state`를 채운 것이고, 순수 노선은 그 둘을
  N/A로 둔 것이다. 즉 **하나의 codec으로 둘 다 처리**한다.
- **ACK는 별도 메시지**(Message ID 3, `Application ACK`).
- 필드는 **S-421(IEC 63173-1)의 이름·열거값을 차용**하되, 좁은 VDE-TER 슬롯에 맞춰
  **압축 비트로 인코딩**했다(S-421 GML 원문이 아님). 상세 논리 모델:
  `docs/mass_roc_control_and_ack_message_format.md`.

---

## 1. 봉투(envelope) 구조와 VPFI

응용이 현재 생성하는 payload 전체 구조:

```text
[ VPFI 16 bit | Message ID 8 bit | 메시지 본문 | byte 정렬 padding ]
```

- **현재 VPFI = `0xFF01`(placeholder)** — IALA R1027 정식 값이 아니다(`common/config.py`).
- **Message ID**: 노선/조종 = `2`, ACK = `3`.

### VPFI 처리 — 링크 팀 결정 필요 (권장안)

VDETER가 VPFI(28-bit)와 wire prefix를 소유하므로, **운영 route 포맷**은 인증서 codec과
같은 방식을 권장한다:

- **응용 body**(우리가 `submit`에 넘길 bytes) = `[ Message ID 8 bit | 본문 | padding ]`
  — 즉 **우리 16-bit VPFI는 제거**하고 넘긴다(우리 쪽 `codec.py` 한 곳만 수정하면 됨).
- **링크 codec**이 route용 VPFI/wire prefix를 붙이고, body 구조를 검증한다.

지금 당장 opaque로 시험 중일 때는 위 §1의 16-bit VPFI 포함 bytes를 그대로 나른다(§5 벡터가
그 형태). 운영 전환 시 위 권장안으로 VPFI만 빼면 된다.

## 2. 노선/조종 본문 — Message ID 2 (`Route Instruction`)

Message ID(8bit) 뒤에 아래 필드가 **이 순서**로 온다(모두 big-endian bit 순서, MSB first).
고정부 **76 bit** + 웨이포인트당 **77 bit**, 마지막에 byte 정렬 padding.

### 2.1 고정부 (76 bit)

| # | 필드 | bit | 형식 | 값·N/A | 의미 |
|---|------|:---:|------|--------|------|
| 1 | Message Linkage ID | 10 | uint | 0 = N/A | ACK가 참조하는 상관 ID |
| 2 | Sender Classification | 3 | uint | 0=ship, 1=authority | 송신자 구분 |
| 3 | Route Type | 5 | uint | 0=N/A,1=mandatory,2=recommended,3=alternative,4=rec-through-ice,5=ship-route-plan,31=cancellation | 항로 종류 |
| 4 | Start Month | 4 | uint | 0 = N/A (1–12) | 유효 시작 월 |
| 5 | Start Day | 5 | uint | 0 = N/A (1–31) | 일 |
| 6 | Start Hour | 5 | uint | 24 = N/A (0–23) | 시 |
| 7 | Start Minute | 6 | uint | 60 = N/A (0–59) | 분 |
| 8 | Duration | 18 | uint | 262143 = N/A | 유효 지속(분) |
| 9 | **Heading Setpoint** | 12 | uint | **3600 = N/A**, scale ×10 → 0.1° (0–359.9°) | 목표 침로. **조종(006)에서 사용** |
| 10 | **Fallback State** | 3 | uint | 0=none,1=Anchoring,2=DynamicPositioning,3=Drifting | **조종(006)에서 사용** |
| 11 | Number of Waypoints | 5 | uint | 0–16 | 웨이포인트 수 n |

> **노선(005)** = 9·10을 N/A(3600·0)로 둔다. **조종(006)** = 9·10을 채운다.
> 나머지는 동일. 그래서 하나의 codec으로 둘 다 처리된다.

### 2.2 웨이포인트 (n번 반복, 각 77 bit)

| # | 필드 | bit | 형식 | 값·N/A | 의미 |
|---|------|:---:|------|--------|------|
| 1 | Longitude | 28 | **int (2의 보수)** | 181°(=108,600,000) = N/A | 경도. 단위 1/10,000분 |
| 2 | Latitude | 27 | **int (2의 보수)** | 91°(=54,600,000) = N/A | 위도. 단위 1/10,000분 |
| 3 | Turn Radius | 10 | uint | 1023 = N/A, scale ×100 → 0.01 NM | 선회반경 |
| 4 | Planned SOG | 10 | uint | 1023 = N/A, scale ×10 → 0.1 kn | 계획 대지속력 |
| 5 | Leg Geometry | 2 | uint | 0=none,1=Lexodrome,2=Orthodrome | 직전→현 웨이포인트 leg 기하 |

### 2.3 좌표 인코딩 (§4 참조)

`raw = round(degrees × 600,000)` (1도 = 60분 × 10,000 = 600,000 단위), 28/27-bit **2의 보수**.
남·서 반구는 음수. 복원: `degrees = raw / 600,000`.

## 3. ACK 본문 — Message ID 3 (`Application ACK`)

Message ID(8bit=3) 뒤 **17 bit** + byte padding.

| # | 필드 | bit | 형식 | 값 | 의미 |
|---|------|:---:|------|-----|------|
| 1 | Message Linkage ID | 10 | uint | 원 노선의 linkage_id | 어느 노선에 대한 ACK인지 상관 |
| 2 | Status | 4 | uint | 0=received, 4=Acknowledged, 7=Errors, 8=Incomplete, 9=Route issues | S-421 상태 코드 |
| 3 | Reason | 3 | uint | 0=none,1=route_unsuitable,2=expired,3=not_authorized | 실패 사유 |

---

## 4. 좌표 인코딩 상세 (`coordinates.py`)

| 항목 | 값 |
|---|---|
| 단위 | 1/10,000 분 (1도 = 600,000 단위) |
| 경도 bit | 28, 2의 보수 |
| 위도 bit | 27, 2의 보수 |
| 경도 N/A | 181° = 108,600,000 |
| 위도 N/A | 91° = 54,600,000 |

예: 경도 129.076° → round(129.076 × 600,000) = 77,445,600 → 28-bit 2의 보수.

## 5. 예시 벡터 (우리 codec 실제 출력, 16-bit VPFI 포함)

> 아래 hex는 **현재 봉투(VPFI 0xFF01 포함)** 형태다. 앞 3바이트 `FF 01 02`는
> `VPFI(0xFF01) + Message ID(0x02)`이고, 그 뒤가 본문이다. 운영 전환 시 앞 2바이트(VPFI)만
> 빠지고 `02 …`(Message ID)부터가 응용 body가 된다.

**노선(SC-VDE-005)** — waypoint 2개(129.076/35.102 SOG 12.5 Lexodrome, 129.333/35.208 SOG 8.0 Orthodrome), 조종필드 없음, linkage_id=7, 32 byte:
```text
FF 01 02 01 C8 40 18 F3 FF FF E1 00 24 9D B9 E0 28 2B CA 01 90 FA A5 00 A1 C1 42 56 C0 1E 05 08
```

**조종(SC-VDE-006)** — heading 92.5°, fallback Anchoring, waypoint 2개, linkage_id=7, 32 byte:
```text
FF 01 02 01 C8 40 18 F3 FF FF 39 D2 24 9D 7C F0 28 2B 34 00 F0 78 A4 EF 91 01 41 A6 F8 07 82 84
```

**ACK(Message ID 3)** — linkage_id=7, status=4(Acknowledged), reason=0, 6 byte:
```text
FF 01 03 01 D0 00
```

codec 검증 시 위 벡터를 디코드해 §2·§3 필드가 복원되면 정합이다. (재현: 저장소
`route_loopback_demo.py`/`control_loopback_demo.py`의 payload 생성부, 또는 요청 시 벡터 추가 제공.)

## 6. 링크 팀에 요청

1. **route/control payload_format 등록** — 위 형식으로 body를 인식·구조 검증하는 codec
   (인증서 `certificate_report` codec에 대응). Message ID 2(노선/조종)·3(ACK)를 한 format에
   담고 Message ID로 분기하거나, 정책에 맞게 분리.
2. **VPFI 배정** — 프로젝트 전용 VPFI(또는 R1027 협의값). 배정되면 우리는 `codec.py`의
   16-bit VPFI 봉투를 제거해 응용 body를 `[Message ID | 본문 | padding]`으로 맞춘다.
3. 등록 후 우리 쪽 작업은 `common/vdeter_bridge.py`의 `PAYLOAD_FORMAT_BY_DATA_TYPE`에
   매핑 한 줄 추가뿐이다 → 노선·조종이 opaque가 아닌 **운영 종단**이 된다.

> 참고: 구조 검증 범위는 codec 정책이다. 최소한 Message ID·waypoint_count 범위(0–16)·
> 본문 길이 일치만 봐도 되고, 필드값 유효성까지 볼지는 링크 팀이 정한다. 신뢰·업무
> 판정(항로 유효성 등)은 응용(MASS/ROC) 책임이다.
